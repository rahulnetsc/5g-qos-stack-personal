# G5's lever, read against the map registered before the hook existed

**2026-09-05.** `docs/g5-ranking-map.md` was committed (`2bffb87`) before
`scheduler/rank_trace.py` was written. It is CLOSED: outcomes L1–L7 (a
ranking term decides) and U1–U4 (the question is unreachable, and how) were
fixed in advance. This document reads the data against it and does not amend
it.

**Answer: U1 — the declaration-order artefact.** Confirmed by permutation,
the same method that established G12's. **The registered ROUTE to U1 is
refuted, and that is reported below as a residual** rather than folded in.

---

## 0. What was run

`scripts/g5_rank_probe.py`, at **G5's own configuration** — n_ues 8, horizon
40,000 slots, load_mult 1.0, `cqi_delay_slots=8`, `record_timeseries=True`:
exactly what `scripts/phase2_core.py` measures G5 with. A measurement carries
its configuration, and a ranking trace taken in a cheaper one would be a
statement about a different system.

**30 runs = 3 arms × 10 paired seeds. All three arms, always** — the
registered cross-arm reading cannot be made from one arm, and
`g5_read_map.py` refuses to read a file missing any of them.

| arm | seeds with a qfi-2 flow under 0.99 | which UE |
|---|---|---|
| **PF** | **0 / 10** | — (worst flow rotates over ue1, 2, 4, 5, 6, 7) |
| **Reservation** | **7 / 10** | **ue8 on 7 of 7** (ue7 also on one) |
| **TwoTier** | **4 / 10** | **{6, 7, 8} on 4 of 4** |

The map's registered background (Reservation 7/10, TwoTier 4/10, PF 0/10)
**reproduces exactly on current code.**

## 1. THE FINDING: which UE fails is set by its POSITION, not by the UE

**All eight UEs are configuration-identical** — same `gfbr_bps` (4 Mbps),
`mfbr_bps` (8 Mbps), `pdb_ms` (150), same `period_ms`/`avg_bytes`/
`fragment_bytes`, and `snr_spread_db` defaults to 0. Nothing distinguishes
ue8 from ue1. Yet the failing set is **the same index on every failing
seed**, across ten different seeds, on both QoS-aware arms.

**The permutation test settles it.** Reversing the flow declaration order:

| arm | seed | forward | reversed |
|---|---|---|---|
| Reservation | 1097657231 | fails **ue8** | fails **ue1** |
| TwoTier | 35492826 | fails **{6, 7, 8}** | fails **{1, 2, 3}** |

Rotating by three instead of reversing, so ue8 moves from last to first:

| | order of qfi-2 flows | failing |
|---|---|---|
| base | `[1,2,3,4,5,6,7,8]` | **ue8** (fraction 0.0) |
| rotated | `[8,1,2,3,4,5,6,7]` | **ue7** (fraction 0.0), **ue8 → 1.0** |

**The failure follows the last position in the list.** ue8's own offered
traffic changed by **+0.5 %** between those two runs while its completeness
went from 0.0 to 1.0.

**The one confound, stated rather than buried:** the traffic is not
bit-identical under a permutation — the generator is order-sensitive, and
per-UE `bytes_arrived` moved by **at most ±1.6 %**. That is why the rotation
was run as well as the reversal: a traffic explanation has no reason to shift
the failing set by *exactly* the permutation applied, twice, in the direction
the permutation predicts.

## 2. The proximate term DIFFERS per arm — which is the registered cross-arm reading

Share of each group's adjacency losses, decided by term. The failing UEs are
compared against **the healthy UEs in the same run**, never against a pooled
across-seed baseline.

**Reservation** (7 failing seeds; 73,728 failing-UE adjacencies vs 1,260,906 healthy):

| term | failing UE | healthy UEs |
|---|---|---|
| **`pdb_ms`** | **86.85 %** | 22.64 % |
| `-coef` | 7.59 % | 65.93 % |
| TIED (declaration order) | 5.38 % | 0.02 % |
| `has_gbr` | 0.18 % | 11.41 % |
| `has_srb` | 0.00 % | 0.00 % |

**TwoTier** (4 failing seeds; 228,019 vs 491,429):

| term | failing UEs | healthy UEs |
|---|---|---|
| `-coef` | 84.51 % | 93.57 % |
| **TIED (declaration order)** | **15.49 %** | 6.43 % |
| **`floor_fire`** | **0.000 %** | **0.000 %** |
| `-floor_sil`, `sched_inactive` | 0.000 % | 0.000 % |

**So the registered cross-arm reading resolves to its second branch:** the
lever is **not** the same term on both QoS-aware arms. Per the map,
*"concentrate-vs-spread" therefore names a shared OUTCOME produced by two
different mechanisms — a description rather than a cause.*

**But both mechanisms are index-determined, and PF's is not.** Full-tie rate
across all ten seeds: **PF 0.01 %, Reservation 0.23 %, TwoTier 3.82 %.** PF
ranks on one continuous float, so it has essentially no tie structure and no
stable-sort bias — and it is the only arm whose worst flow rotates freely
across UEs. PF is the control, and it behaves like one.

### L1 is refuted, and it is worth saying plainly
`floor_fire` decides **0.000 %** of adjacencies on TwoTier, on either group.
The UL service-interval floor was newly reachable this campaign — `mfbr_bps`
has been configured since `3788202`, and before that the gate was true zero
times in 424,959 calls. **It is now armable and still never decides a
ranking.** L1 registered it as a live candidate; it is not the lever.

## 3. THE RESIDUAL: U1's outcome is confirmed, U1's registered ROUTE is not

U1 as registered reads: *"every term is tied and the sort falls back to list
position."* That is **TwoTier's minority mechanism and is not Reservation's
at all.**

- **TwoTier**: 3.82 % of adjacencies are fully tied, **71.2 % of them at
  `coef == 0.0`**. Python's sort is stable, so every tie resolves in favour
  of the earlier list position. A 4 % tie rate compounding over 32,000
  ranked slots is what produces a permanent per-index service deficit —
  a *bias*, not a fallback.
- **Reservation**: the deciding term is `pdb_ms`, not a tie. The
  last-position UE carries **`pdb_ms = 9999`**, the `_ul_gbr_and_pdb`
  "no eligible LCG" sentinel (`gNB_scheduler_ulsch.c:2223`), so it loses
  tier 3 to every UE holding a real PDB.

**Verified directly rather than argued** — the project's own rule that an
inference about existing code is a hypothesis until run. Wrapping the real
`_ul_gbr_and_pdb` and calling it (behaviour-preserving), seed 1097657231:

| ue | candidate evaluations | all per-LCG estimates == 0 | any `bytes_reported` > 0 | ever `has_gbr` |
|---|---|---|---|---|
| 1–5 | ~30,900 each | **1 (0.0 %)** | 100 % | yes (~29 %) |
| 6–7 | ~30,950 each | 31 (0.1 %) | 100 % | yes (~29 %) |
| **8** | **9,216** | **9,216 (100.0 %)** | **9,216 (100.0 %)** | **never** |

**ue8 is eligible on 100 % of its slots and carries no QoS state on 100 % of
them.** Eligibility reads `bytes_reported`; the ranking tiers read
`estimated_ul_buffer_per_lcg`. Those are two different BSR-derived views, and
CLAUDE.md's own invariant already records that they *legitimately desync
between BSRs*. What is new is that for the last-position UE the per-LCG array
is **never populated at all** — not populated-then-collapsed — so the desync
is permanent, and the UE enters every sort it participates in as though it
had no bearer configured.

**That is a cold-start lock-in one level over the documented one.**
`sim/ul_access.py` was built to break exactly this deadlock for the scalar
`bytes_reported`; it does not arm the per-LCG array, and the per-LCG array is
what two of Reservation's four ranking tiers read.

**Why this is a residual and not L3 or U2.** L3 registered *"the deficit was
satisfied or reset when it should not have been"* — it was never set. U2
registered *"the flow is not in the candidate set"* — it is, on 9,216 slots.
The measured shape is a third thing: **present and eligible, while every
QoS-bearing term on the candidate reads its no-information sentinel.**

## 4. Two things the scope finding closes

**G5 and G10's camera question are two statistics on one flow.** `*_qfi2` is
the camera; M05 (completeness) and M08 (GFBR fraction) read the same UL
`xr_video` flow. The camera question's answer — *the UE is granted rarely,
not short-changed when granted* — and this one — *it is granted rarely
because it starts last and never recovers* — are one result. **Both threads
close together.**

**G5 as measured is a UL-only guarantee on this workload, and that is a
property of the workload rather than a limit of the trace.** M05/M06 read
`FlowRecord.frame_completions`, which `FrameLedger` populates only for flows
carrying a `frame_id`, and `sim/traffic.py` assigns one only in
`_gen_xr_video`. The parametric mix's only DL flow is `qfi 82
periodic_control`. **No DL flow has PDU-set structure**, so neither arm's DL
ranking key can decide anything for G5. A reader will assume a completeness
guarantee covers both directions; on this workload it does not.

---

## 5. What this does NOT say

- **It does not say the schedulers are wrong.** A stable sort with a
  deterministic tie-break is a legitimate implementation. What it says is
  that **G5's measured outcome on this workload has no physical referent**:
  with eight identical UEs, "which UE fails" is a fact about list position.
- **It does not say the failure magnitude is an artefact.** Reservation's
  trapped UE really does complete 0 of 299 frames within its PDB. The
  starvation is real; its *victim* is arbitrary.
- **It does not re-score G5.** Whether a guarantee whose victim is
  index-determined should count as a failure is a specification question,
  and specification questions are not settled by the run that found them.
